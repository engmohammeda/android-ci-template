# 🚀 تشريح خط الإصدار خطوة بخطوة

## نظرة عامة

```
push إلى main
   │
   ├─ 1. Checkout كامل التاريخ (fetch-depth: 0) ─ لازم لحساب semver من الوسوم
   ├─ 2. JDK 17 + Android SDK (platform 36 + build-tools 36)
   ├─ 3. استعادة Gradle Wrapper إن فُقد الـ jar
   ├─ 4. google-services.json (فقط عند تبنّي Firebase)
   ├─ 5. تجهيز التوقيع (إنتاجي من KEYSTORE_BASE64 أو debug تلقائي)
   ├─ 6. 🚧 بوابة الاختبارات ─ فشلها = لا نشر إطلاقاً
   ├─ 7. حساب SemVer + ملاحظات مصنّفة من رسائل commits
   ├─ 8. ختم النسخة في build.gradle.kts (sed على versionName)
   ├─ 9. بناء Debug APK + Release APK + AAB
   ├─ 10. تجميع dist/ + بصمات SHA256 + أحجام
   ├─ 11. رفع mapping.txt (فك تعمية R8) كأثر لمدة 90 يوماً
   ├─ 12. store-lint (تحذيري، يكسر فقط عند طلب نشر Play)
   ├─ 13. إنشاء GitHub Release بوسم vX.Y.Z-build.N
   ├─ 14. بناء ونشر صفحة الخصوصية على Pages
   ├─ 15. إرسال تلجرام (رسالة + 3 ملفات)
   ├─ 16. Google Play internal (اختياري)
   └─ 17. Job Summary ─ جدول حالة نهائي
```

## قرارات تصميمية مهمة

### لماذا الاختبارات قبل حساب النسخة؟
لأن فشلها يجب أن يوقف كل شيء قبل إنشاء أي وسم أو أثر — لا نلوّث تاريخ الإصدارات بنسخ فاشلة.

### لماذا `versionCode = GITHUB_RUN_NUMBER`؟
رقم تشغيل GitHub متزايد دائماً وفريد، ما يضمن قبول Play للحزمة الجديدة دون إدارة يدوية.

### لماذا وسم بصيغة `vX.Y.Z-build.N`؟
- `X.Y.Z` دلالي يفهمه البشر.
- `build.N` يضمن التفرد حتى لو أُعيد البناء بنفس النسخة.
- منطق حساب semver يقبل الصيغتين عند البحث عن آخر وسم.

### لماذا mapping.txt؟
نسخة release معمّاة بـ R8. عند ورود تقرير عطل (crash) من مستخدم، تحتاج هذا الملف لفك أسماء الدوال. يُحفظ 90 يوماً لكل إصدار.

### لماذا bitrot أسبوعي؟
اعتمادات وأدوات البناء تتقادم بصمت. البناء الأسبوعي يكشف الانكسار مبكراً بدل اكتشافه يوم تحتاج إصداراً عاجلاً.

## بوابات الفشل

| البوابة | متى تكسر البناء؟ |
|---|---|
| Unit tests | دائماً (إلا بإيقاف يدوي صريح) |
| google-services | فقط إذا تبنّى المشروع Firebase بلا إعداد صالح |
| store-lint | فقط عند `publish_play = true` مع أوصاف تتجاوز حدود Play |
| lint | لا يكسر أبداً (تقرير توجيهي) |
